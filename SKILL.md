# CompareX Engineering Protocol (SOURCE OF TRUTH)

This file is the permanent, authoritative reference for all development sessions
on the CompareX project (Product Comparison & Recommendation Assistant).
Every agent session (Antigravity, Claude, or human) MUST read this file first
and MUST NOT contradict it. If a task appears to require breaking a rule here,
STOP and flag it — do not silently work around it.

---

## 1. Project Identity

CompareX is a multi-domain product comparison and recommendation platform for
real users — NOT a chatbot. Chat is one entry point among several, not the
product itself. The product surface must work correctly for a user who never
types a single message.

Recommendations come from real models trained on real interaction data — the
system is a recommender engine with an LLM explanation layer on top, NOT an
LLM wrapper that guesses.

Data source: https://github.com/caserec/Datasets-for-Recommender-Systems
Primary domain: RetailrocketEcommerce (implicit feedback: views/cart/purchase)
Secondary domain: Steam (implicit feedback + price/genre metadata)
Explicit-feedback proof domain: BookCrossing (ratings 1-10 + implicit flag)

Domain data reality (confirmed via Phase 0 data audit, see docs/data_dictionary.md):
none of the three domains have timestamps in their processed source data — this
is expected, not a defect, and the normalized schema's timestamp field will
always be None for these domains. Metadata richness varies significantly:
- RetailrocketEcommerce: no metadata at all (fully anonymized IDs only).
  This is the pure collaborative-filtering proof domain — strong for model
  metrics (Admin view), weak for Browse/Compare visual display.
- Steam: title only, no category/price/genre. Middle ground.
- BookCrossing: rich metadata (title, author, year, publisher, cover images).
  This is the primary UI-showcase domain — Browse/Compare should lead with
  this domain when demonstrating visual polish.
Per Section 4's rule, any missing metadata field renders as "not specified" —
never fabricated. Retailrocket and Steam will exercise this rule more visibly
than BookCrossing.

Domain scope is frozen at exactly these three for the initial build. If a
future session encounters additional domains in the source repo (e.g. Anime,
AmazonMusic) during exploration, it may document them for awareness but must
NOT scaffold, implement, or plan around them without explicit human approval
first. Adding a domain later is expected to be low-cost (Section 4's frozen
interface exists for this reason) — but it is always an explicit decision,
never an inferred one.

## 1a. Required Product Surfaces (Frontend)

The frontend MUST implement four surfaces. Surfaces 1-3 are backed by the SAME
recommender service and are not separate code paths; surface 4 is a read-only
view onto system metrics:

1. **Browse/Search** — filterable product grid per domain (price, category,
   rating, etc.), calling `get_recommendations()` / `cold_start_recommend()`
   directly. Must work with ZERO chat interaction — this is the baseline
   product a real user lands on.
2. **Compare** — user selects 2-4 items (from Browse or search) and views a
   structured comparison table, generated by `compare()`. Must be reachable
   without ever opening chat.
3. **Assistant (chat)** — a conversational layer on top of surfaces 1 and 2.
   Narrows filters, explains recommendations, answers "why this item," and
   can trigger Browse/Compare actions on the user's behalf. It is a
   convenience layer, not a dependency — if the LLM is rate-limited or down,
   Browse and Compare must continue to work normally.
4. **Admin/Analytics view** — an internal, auth-gated dashboard (not
   user-facing) showing: request volume per domain, model evaluation metrics
   (precision@K/NDCG per domain), baseline-vs-hybrid comparison, and recent
   feedback-loop activity (new interactions logged, last retrain timestamp).
   This is what turns "trust it works" into visible evidence for judges/
   stakeholders and is required, not optional, for an industry-level bar.

Rule: the chat surface must never be the only way to reach a piece of
functionality. If a capability only exists "through the assistant," it is
incomplete — it must also be reachable through Browse/Compare UI actions.

## 2. Non-Negotiable Architectural Rule

**The recommendation engine is the deterministic source of truth.**
**The LLM is for explanation, comparison formatting, RAG, and intent
routing ONLY.**

The LLM must NEVER:
- Generate a ranked recommendation from its own knowledge/guessing
- Invent a product spec, price, or attribute not present in the database
- Substitute for the hybrid recommender when the recommender returns a result

The LLM MAY:
- Explain why the recommender chose an item
- Format ranked results and comparisons into structured JSON/natural language
- Classify user intent (recommend vs. compare) and extract constraints
- Ask clarifying questions when intent/domain is ambiguous
- Power RAG-based Q&A over product descriptions (grounded, cited to source docs)

## 4. Frozen Service Contract

Every domain (Retailrocket, Steam, BookCrossing, and any future dataset) MUST
implement this identical interface. The interface is defined once, in the
FastAPI ML service, and is never modified per-domain — only implemented.

```python
class BaseRecommenderService(Protocol):
    def get_recommendations(
        self, user_profile: UserProfile, constraints: Constraints
    ) -> list[RankedItem]: ...

    def compare(self, item_ids: list[str]) -> ComparisonTable: ...

    def cold_start_recommend(
        self, preference_answers: dict
    ) -> list[RankedItem]: ...

    def explain(self, item_id: str, user_profile: UserProfile) -> str: ...
```

Note on `explain()`: this returns the RAW factual reasoning (e.g.
"matched_constraints=['budget<=1200'], similarity_basis='co-purchased with
item X'") — plain data, not natural language. It is NOT the user-facing
explanation. The LLM's `explain_recommendation()` (Section 4a) is what turns
this raw reasoning into natural language for the user. `explain()` must work
and return something meaningful even if the LLM layer is completely down,
since Browse/Compare must survive Gemini being unavailable (Section 1a).

Rules:
- `ComparisonTable` fields must trace back to real database records. If a field
  is unavailable, return "not specified" — never fabricate.
- If a real model fails to load/predict, fall back to a popularity baseline
  rather than raising an unhandled error to the user.
- Adding a new domain = writing a new class implementing this interface.
  It must NEVER require editing the interface itself, the Node.js gateway,
  or the frontend. If it does, the interface was under-specified — fix the
  interface deliberately and update this file, don't patch around it.

## 4a. LLM Provider Abstraction (Mandatory)

The LLM provider has changed once already during planning (Claude -> Gemini).
To ensure a third change never costs a rewrite, the FastAPI service MUST
access the LLM only through a thin internal interface:

```python
class BaseLLMClient(Protocol):
    def classify_intent(self, user_message: str, history: list) -> IntentResult: ...
    def extract_constraints(self, user_message: str) -> Constraints: ...
    def format_comparison(self, comparison_data: ComparisonTable) -> str: ...
    def explain_recommendation(self, item: RankedItem, user_profile: UserProfile) -> str: ...
```

Rules:
- No code outside `llm/gemini_client.py` (the concrete implementation) may
  import the Gemini SDK directly.
- All structured-output calls (constraint extraction, comparison formatting)
  must request/validate JSON output and be checked against source data before
  returning to the user — this rule is provider-independent and non-negotiable.
- Gemini free-tier rate limits: implement retry-with-backoff and a graceful
  degraded response ("still thinking, one moment") rather than surfacing raw
  API errors to the user.
- API key is loaded via env var (`GEMINI_API_KEY`) only, never hardcoded,
  never sent to the frontend.

## 4b. Feedback Loop (Mandatory)

The system must not be frozen at initial training. Every real user interaction
across all three surfaces (Browse, Compare, Assistant) is logged back into
MongoDB as a new `interactions` record (event_type: "view", "compare_select",
"click", "cold_start_answer"), tagged with a session/user id and domain.

- A retraining script (`scripts/retrain_domain.py <domain>`) folds new
  interactions into that domain's model. Manual trigger is acceptable for the
  hackathon; a scheduled job is the production-grade next step.
- Retraining one domain's model must never affect another domain's artifacts
  (see Section 5, model versioning).
- This is what allows the system to genuinely improve from real usage rather
  than being a static demo running on the original caserec snapshot forever.

## 4c. Explainability Data Contract (Mandatory)

The LLM does not invent explanations. `get_recommendations()` must return the
"why" alongside the "what" so the LLM has real signal to format into language:

```python
class RankedItem(BaseModel):
    item_id: str
    score: float
    matched_constraints: list[str]      # e.g. ["budget<=1200", "category=laptop"]
    similarity_basis: str | None        # e.g. "users who interacted with X also chose this"
    domain: str
```

The LLM's `explain_recommendation()` call receives this structured data and
formats it into natural language. It never receives just an item_id and asked
to guess a justification.

---

## 4d. Empty-Result & Edge-Case Behavior (Mandatory)

`get_recommendations()` and `cold_start_recommend()` must never return an
empty result with no explanation. Required fallback sequence:
1. Try exact constraints
2. If < N results, relax the least-important constraint (documented ranking:
   category > budget-hard-cap > secondary filters) and retry, tagging the
   response as `relaxed: true` with which constraint was relaxed
3. If still empty, return a "no exact matches" response with the closest
   available items and a clear reason — never a blank UI state or raw error

## 5. Data Handling Rules

- All datasets are sourced from the caserec repo (or equivalent real data) —
  no synthetic/fabricated interaction data in production paths.
- Each dataset's own README (in the repo) is the data dictionary. Schema is
  never guessed; it is read from source before any pipeline code is written.
- User data collected in production (real users) follows the same hashing/
  anonymization discipline the Retailrocket dataset itself uses — no raw PII
  stored unnecessarily.
- Model artifacts are versioned (file naming + manifest at minimum). Retraining
  one domain's model must never silently affect another domain's artifacts.

---

## 5a. Data Integration Steps (Canonical Order — Do Not Reorder)

1. Clone `caserec/Datasets-for-Recommender-Systems` and read each domain's
   own README first — no schema is ever guessed.
2. Copy raw files into `data/raw/<domain>/` inside this repo. The original
   GitHub repo is a one-time source, never a runtime dependency — after this
   step it is never touched again.
3. Write one ingestion script per domain, each outputting the SAME normalized
   shape (see schema below) regardless of source format differences.
4. Load normalized data into MongoDB Atlas (`interactions`, `items`
   collections), indexed on `(user_id, domain)` and `(item_id, domain)`.
   Generate embeddings for item metadata for Vector Search.
5. Train models offline per domain (ALS for implicit, matrix factorization
   for explicit) from `data/processed/` or Mongo. Save versioned artifacts
   to `models/`, tracked in `manifest.json`.
6. Wire trained artifacts into each domain's service class (Section 4).
7. Validate via offline evaluation (precision@K/NDCG) and a direct smoke test
   of `get_recommendations()`/`compare()` before connecting UI or LLM layers.

```python
# Normalized interaction record (every domain maps to this)
{
  "user_id": str, "item_id": str, "domain": str,
  "event_type": str,       # "view"|"cart"|"purchase"|"rating"|"play"|"compare_select"
  "value": float | None,   # rating score, playtime, etc.
  "timestamp": int | None  # confirmed always None for retailrocket/steam/bookcrossing
                            # (source data has no timestamps) — do not treat this
                            # as a bug when building recency-based features later
}

# Normalized item record
{
  "item_id": str, "domain": str, "title": str,
  "category": str | None, "price": float | None, "metadata": dict
}
```

## 6. Security Rules (Non-Negotiable)

- No secrets (Gemini API key, Mongo URI, JWT secret) ever committed to the
  repo or exposed to the frontend. Env vars / secret manager only.
- All backend routes require JWT auth except explicit public endpoints
  (health check, public demo mode if applicable).
- Helmet + CORS + rate limiting enabled on the Express gateway from day one,
  not added later.
- Input validation (Pydantic on FastAPI, equivalent on Express) at every
  service boundary. No unvalidated input reaches the recommender or the LLM.

## 8. Definition of Done (Per Domain Service)

A domain service is NOT done until:
1. It implements the full `BaseRecommenderService` interface
2. It has a popularity-baseline fallback that works independently of the real model
3. It has cold-start handling for zero-history users
4. It has an offline evaluation report (precision@K, recall@K, or NDCG) checked in
5. `compare()` output has been verified to never emit a field absent from source data
6. It passes its own isolated test suite AND the full regression suite (other
   domains still work unchanged)

---

## 9. Definition of Done (Product-Level, Not Just Backend)

The project is NOT complete when the API works. It is complete when:
1. A real user can land on Browse, filter, and see real recommendations with
   zero chat interaction
2. A real user can select items and view a working Compare table with zero
   chat interaction
3. The Assistant surface can perform every action Browse/Compare can, as a
   convenience — but is never the sole path to any feature
4. If the LLM (Gemini) is unavailable or rate-limited, Browse and Compare
   continue to function normally — only the Assistant surface degrades
5. All three domain services meet Section 8's per-domain Definition of Done
6. Real interactions from all surfaces are being logged back into MongoDB
   (Section 4b) and at least one retrain cycle has been demonstrated
7. Recommendations carry structured "why" data (Section 4c) and the LLM's
   explanations are visibly grounded in that data, not generic
8. Empty/edge-case queries produce a graceful relaxed-constraint response,
   never a blank state or raw error (Section 4d)
9. The Admin/Analytics view is live and auth-gated, showing real metrics
   (request volume, precision@K/NDCG per domain, baseline-vs-hybrid
   comparison, last retrain timestamp)
